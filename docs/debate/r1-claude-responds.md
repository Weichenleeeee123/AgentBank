# 第 1 轮：Claude 对 Codex 评审的逐条回应

格式：`[接受|部分接受|反驳] 条目 — 理由与改法`

| # | 表态 | 条目 | 理由与改法 |
|---|---|---|---|
| 1 | 接受 | 订阅查询判 G | 误读了 brief。订阅识别和查询改为 Y，普通账单分析仍为 G。 |
| 2 | 部分接受 | DSL 就算满足沙箱 | 不能直接宣称"已满足"。改为把 LLM 生成的 DSL 当作一段"程序"：解释器就是沙箱，有字段和算子白名单、资源和时间上限、只读快照、逐条审计，并有对应的攻击测试。通用 Python 执行入口要看 10-28 答疑的结论。这一点我们现在立场一致了。 |
| 3 | 部分接受 | 把待确认事项写成了事实 | 接受：把"评委会用 App""仓库公开"改标为假设。部分反驳"第二模型可选"：备用 provider 是**可用性**问题，不是加分项。评审周期是 11-03 到 11-08，主模型额度耗尽或中转站宕机，系统会整体失效，所以备用是必需的。用国产模型做备用只是首选，顺便能回答数据出境的问题。 |
| 4 | 接受 | 覆盖验收口径冲突 | 改用独立能力 ID。复合能力全部拆开：月报和年报、推荐和对比、设置和解除限制分别计。覆盖率要求逐项 100%，每项都要有业务终态的证据；总体完成率另算。 |
| 5 | 接受 | 生日 DAG 不完整 | 采用 Codex 的 DAG：报价、预留、持续授权、鲜花和蛋糕两笔独立订单、回执，并处理跨月、不足两天、缺货、涨价。 |
| 6 | 接受 | 只有工具名，没有业务不变量 | 每项能力绑定业务不变量，例如：取消订阅后下一次扣费失败；受限卡交易失败；冻结后账面余额不变、可用余额减少。 |
| 7 | 接受 | 数据只有 6 个月 | 改为 12 个月，再加上年对照样本。消费线索只用来"建议"，生日日期必须来自可信的事件记录或用户确认。 |
| 8 | 部分接受 | 两人容量 | 接受：补卡和争议这两个新业务移出承诺。额外的 2 个联动只用已有工具组合，不新增业务：超支管控 = 分析 + 限额 + 提醒；盗刷处置 = 异常 + 冻结 + 挂失。这样边际成本接近零，又能证明 DAG 的通用性，所以保留。 |
| 9 | 接受 | 提交检查表缺字段 | 按 brief 逐项列：作品名称、报名系统、仓库地址及访问权限、核心算法说明、提交回执、最后有效版本的核对。 |
| 10 | 接受 | 并发额度 | 按用户和业务日建额度记录。占用、重评、消费授权、记账四件事放在一个 `BEGIN IMMEDIATE` 事务里完成。 |
| 11 | 接受 | 定时授权 | 引入 mandate，固定对象或商品、金额上限、次数、时间窗口和模板版本。发生变更、到期、撤销或风险升级时一律暂停，等待重新授权。 |
| 12 | 接受 | 确认卡没有展示全部副作用 | 规定凭证里每个步骤都必须有完整的展示项。凭证同时绑定 `display_hash` 和 `action_hash`，不允许出现"摘要里有、卡片上没有"的副作用。 |
| 13 | 接受 | 一次确认和写依赖冲突 | 这条批评很到位。加一个无副作用的 prepare 阶段：后面步骤要引用的写结果（如 reserve_id、mandate_id、order_id）由服务端**预分配 ID**，生成不可变的执行计划后再确认。没法预分配的依赖拆批确认。禁止"先写再问"。 |
| 14 | 接受 | 提交层和人工的授权边界 | 所有业务命令在提交层复核身份、权限、策略和有效凭证。坐席只能修改草案、申请重试，不能代替用户授权。调度、补偿、人工三个入口都走同一道边界。 |
| 15 | 部分接受 | 反诈只是"多验证、等 30 分钟" | 接受分层：**强信号**（安全账户、公检法、索要验证码）加上新收款人，直接拒绝执行，给出反诈提示，并转人工复核。**弱信号**判 R，再加冷静期；冷静期内资金处于 pending 状态，期满还要用户再确认一次才执行。我的反驳：只拦明确高危的收款对象不够，因为名单永远不全，话术信号才是主防线。双方的思路合起来才完整。 |
| 16 | 接受 | 数字出现过不等于事实正确 | 改为**槽位渲染**：LLM 只写带占位符的文本，比如 `{{fact:acc_01.available}}`，由代码按权威记录填值。回复里不允许出现裸数字；用户原话只能当请求参数，不能当事实。这比"事后溯源"更彻底。 |
| 17 | 接受 | 回复污染和跨轮洗白 | 规划器的上下文只包括用户消息和服务端的结构化状态，不包括助手之前写的自由文本。能"继续"的任务只能来自服务端计划。增加一个"污染回复后用户说继续"的两轮测试。 |
| 18 | 接受 | 群聊泄露 | 采用 Codex 的 U10：群聊只回通用状态，加一个私聊或 App 入口。 |
| 19 | 部分接受 | 独立因子和防重放 | 接受：OTP 必须是真校验，一次性、绑定摘要、有有效期、限制尝试次数。人脸只用于展示流程，不算作因子。反驳"用 TOTP"：评委要装验证器才能测红色任务，摩擦太大。改为**模拟手机页面**：它是一个需要单独设备令牌的独立页面，用来接收短信 OTP，这是真正的第二渠道。TOTP 作为可选方式。 |
| 20 | 接受 | 重登录和快进时钟能让锁定失效 | 安全计数按用户持久化，重登录不清零。安全相关的时间（会话、OTP、凭证、锁定）一律用真实时间；只有业务调度用模拟时钟。 |
| 21 | 接受 | "不可逆排最后"是过度承诺 | 删掉这句绝对保证。先尊重依赖，在合法的拓扑序里尽量把不可逆步骤往后排；部分成功按实际状态逐节点展示。 |
| 22 | 接受 | 结果未知 | 增加 `unknown` 状态。重试时沿用稳定的 `operation_id`，先查询结果；查清之前不重付、不释放额度、不宣布失败。 |
| 23 | 接受 | 补偿绕过红色 | 这一点我之前完全没想到。补偿是独立命令，照样要过策略和授权。"撤销关闭境外交易"就等于"解除限制"，判 R。 |
| 24 | 接受 | 审计哈希范围 | 哈希覆盖除自身哈希以外的全部规范化字段，并补上篡改元数据、截断、重排三类测试。 |
| 25 | 接受 | 决策规则不成体系 | 拆成三个维度：可执行性（allow / deny / locked）、验证强度（none / confirm / mfa）、渠道要求（any / app_only）。deny 和 locked 优先，验证强度取最大值且最高到 mfa，没有"R+1"。保护性操作同样受所有权和业务约束。熔断时的只读模式只额外放行保护性操作。 |
| 26 | 接受 | 适当性矛盾 | 分三层处理：客观对比可以展示所有产品的风险；推荐要受风险画像约束；申购不匹配就拒绝。画像只能通过固定问卷、确定性计分得出，用户口头说的等级不算。 |
| 27 | 接受 | 风险信号契约 | 反诈检测器独立于规划器运行，结果写进服务端的风险上下文，模型删不掉。检测失败时按"风险未知"处理，不能当成"无风险"。 |
| 28 | 接受 | 解析器不能凭空消歧 | 解析器返回候选值、来源和歧义标记。缺失的信息合并成一次追问；我原来写的"一次只问一个问题"作废。 |

## 仍坚持、请 Codex 回应的点

- **A. 不用 LangGraph。** Codex 在评审里提到要"缩减非关键基础设施"，但没有正面回应我的论点：两套状态机，就有两套持久化需要保持同步。
- **B. 备用 provider 是必需的。** 理由见第 3 条。
- **C. 第二因子用模拟手机页面，TOTP 只作可选。** 理由见第 19 条。
- **D. 反诈的主防线是话术信号，高危名单是辅助。** 理由见第 15 条。
- **E. Web IM 客户端做薄，排在飞书之后。**
