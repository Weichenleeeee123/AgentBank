**一、回应 Claude 对我的 12 条问题评审**

1. [接受] 诱导转账只靠风险名单和 MFA — 原方案确实漏掉了“用户本人受骗后主动授权”的情况。陌生账户不在名单中，用户通过 TOTP，仍可能完成诈骗转账。增加独立反诈检测及服务端风险上下文；明确诈骗语义触发暂停或拒绝当前付款，不能靠 MFA、等待 30 分钟自动解除。冷静期内必须尚未付款，不能把已转出资金描述成可撤回。

2. [接受] 间接注入只有“分区”，没有充分机制 — 原方案没有明确禁止外部自由文本进入规划器，隔离要求不够具体。采纳 `untrusted_output_fields`、结构化引用及参数来源校验。但字段标记应由服务端工具契约确定，不能让模型自报来源。按“房东”备注找人仍可由受限解析工具返回候选 ID，原始备注不能变成新增转账指令。验收要检查恶意备注是否生成额外付款计划，不能只检查最终有没有扣款。

3. [部分接受] 技术栈过重、两人排期不成立 — 接受缩减：首版采用 SQLite、单一业务状态存储，外部 IM 联调移出 M1，通用代码沙箱是否加入由答疑结果决定。拒绝“SQLite 单写者使并发竞争直接消失”的表述：如果额度检查发生在事务外，两笔 600 元仍可能都拿到黄色许可。额度读取、重评、授权消费和记账必须进入同一写事务；重放、未知结果和跨渠道累计仍需独立约束。

4. [接受] LangGraph 与自定义 DAG 形成重复状态管理 — 本次首版不使用 LangGraph。原方案同时承诺 checkpoint 恢复和业务节点恢复，却没有定义两者不一致时谁说了算；这项复杂度没有对应的必要收益。对话只保存槽位、实体引用及当前计划版本，执行状态统一由数据库维护。该结论针对本项目期限，不等于 LangGraph 天然不适合金融业务。

5. [部分接受] 420 次 LLM 运行拖慢迭代 — 接受分层评测，但原方案写的是 420 次任务运行，不是 420 次模型调用，也没有要求每次提交都全跑。确定性测试每次提交运行；合并时跑覆盖主要能力和攻击类型的冒烟集；候选发布版再跑完整评测及随机性重复。60 条、310 条、重复两次或三次都应服从实际耗时和覆盖证据，修改样本规模后同步修改报告分母，不能沿用旧成功率。

6. [部分接受] TOTP 给评委增加操作负担 — 接受降低演示摩擦，也接受隔离的模拟短信页面作为流程演示。不接受“brief 没列 TOTP，所以不适合”的理由：原文有“等多因子认证”，不是封闭名单。更不能仅凭另开页面就宣称独立因子成立；如果 App 会话能获取或重置设备令牌，攻击者取得会话后就能同时拿到验证码。TOTP 可降为可选，但替代方案必须证明独立凭据的注册、访问和恢复边界。

7. [接受] 挂失缺少快速止损通道 — 增加独立的临时冻结状态，黄色确认后立即阻断相关卡交易，再进行红色挂失。冻结不等于正式挂失，不能借改名绕过 brief 的红色要求；解除冻结也不能复用原黄色授权。验收直接尝试冻结后的模拟支付，并测试“撤销刚才的冻结”是否重新要求强验证。

8. [部分接受] 跨场景只演生日不足以证明通用性 — 接受增加非生日组合测试，不接受立即增加两个完整产品承诺。原评审提出的补卡、争议属于新增业务，Claude 已在回应中撤回。剩余组合也并非零成本：商户类别限额不同于卡总限额，超支提醒不同于续费提醒，都需要相应状态和执行检查。先用现有工具验证换参数、改依赖、中断及部分失败；新增能力必须单独估时。

9. [接受] 防幻觉没有覆盖聊天正文 — 原文只限制“进入交易结果卡”的资金数字，约束范围确实不够。账户事实、金额、对象、时间和交易状态必须覆盖正文与卡片，绑定同一权威记录。我采纳 Claude 回应第 16 条的槽位渲染方向，不采用简单的“数字在结果里出现过即可”：收入 8000、支出 3000 被交换标签，也能通过数字匹配。事实槽位还必须校验字段语义，不能允许模型任意搭配标签。

10. [部分接受] 单一模型缺乏备用和数据流向说明 — 接受准备经过验证的独立备用 provider，撤回把它仅视为模型对照加分项的定位。但“模型故障导致整个系统不可用”不准确：原方案 §10 已明确，符合条件的已授权确定性调度仍可运行。备用切换只处理模型请求失败，不重建已提交业务操作。数据流向必须另行说明；国产模型品牌不能证明服务端点、代理、日志和存储均在境内。

11. [部分接受] Web IM 投入产出比低，应排在飞书之后 — 接受做薄，复用聊天与卡片组件，只保留独立身份、消息入口、回调和跳转。不同意无条件排在飞书之后：如果评委无法进入租户，Web IM 是可亲手测试跨渠道边界的入口。优先顺序应由租户可用性和实际联调成本决定；模拟渠道必须明确标注，不能冒充真实飞书接入。

12. [接受] 队长兼任安全、规划与集成形成瓶颈 — 安全内核和规划器只通过冻结契约交互，第二人从 M1 就复核伪造授权、重复提交、并发额度等关键测试，M2 后接手更完整的红队集。交叉验证不能等到业务全部铺开以后才开始。它也不能替代工作量缩减，必须与前述技术栈收缩一起执行。

**三、仍未达成一致的分歧**

- [坚持] 第二因子的默认实现与证明标准 — **Claude：**独立设备令牌的模拟手机页面作为默认方式，TOTP 可选。**我：**可以接受该方向，但当前说明不足以证明凭据独立，不能直接认定它已满足真实第二因子要求。**裁决标准：**仅持有 App 会话时，能否注册替代设备、重置令牌或读取 OTP；另测跨操作重放、过期和错误次数限制。以测试结果及 10-28 对模拟验证的答复裁决。

- [坚持] 两个额外联动是否成为首版承诺 — **Claude：**复用现有工具，边际成本接近零，应保留两个完整联动。**我：**保留非生日组合测试；新增类别限额、提醒语义及完整恢复流程需单独估时。**裁决标准：**逐节点核对工具契约、持久化状态和失败用例；以不影响 11-01 首次有效提交、11-02 截止前完成为准。

- [坚持] 诈骗阻断的条件与信号优先级 — **Claude：**话术是主防线，强信号加新收款人直接拒绝，弱信号走 MFA、冷静期和再确认。**我：**明确诈骗语义不能依赖“新收款人”条件；已有收款人同样可能危险，关键词也可能误伤正常付款。**裁决标准：**使用未知账户、先小额试转、既有联系人受骗、语义改写及合法近似表达组成的测试集，同时报告漏拦和误拦。以 brief 的诱导转账防御和交互体验要求共同裁决。

- [坚持] 飞书与薄 Web IM 的实施顺序 — **Claude：**飞书优先，Web IM 在后。**我：**顺序取决于租户权限、联调成本和评委能否亲测，外部接入受阻时优先薄 Web IM。**裁决标准：**10-28 的实际接入结果，以及评委能否复现身份绑定、跳转、重放和群聊隐私测试；模拟渠道与真实平台接入分别标注。

- [坚持] 国产备用能否作为数据出境问题的答案 — **Claude：**接入国产备用可以顺便回答数据出境。**我：**主备全链路的数据去向才是证据，模型国别和备用存在均不足以证明。**裁决标准：**检查实际请求端点、代理、发送字段及日志留存说明；以真实部署事实回答，不把团队选型写成 brief 的官方要求。
