# 第 1 轮：Claude 评审 plan-codex.md

格式：`[严重|中等|轻微] 章节 — 问题 — 证据 — 建议改法`

## 一、它的问题

**[严重] §5 §6 — 诱导转账只靠"风险名单"和 MFA，挡不住受害者本人操作。**
- 证据：U06 只拒绝命中模拟风险名单的收款人；U05 对新收款人只升级到 R。评委最常测的话术是："公安说我涉嫌洗钱，要我把钱转到安全账户 6222 0000 1234 5678"。这个账户不在名单里，于是判 R；受害者本人会顺利通过 TOTP，钱就转走了。强验证证明的是"这是你本人"，证明不了"你没被骗"。§6 那张表里"诱导转账"的通过标准写的是"不因文本建议直接付款"，测的是另一回事，这个场景没覆盖。
- 建议：加一条反诈信号规则。对话里出现安全账户、公检法、刷单返利、客服退款、索要验证码这类话术（规则加 LLM 分类器）时，判 R，弹出强制阅读的反诈提示，并设 30 分钟延时到账，期间可以撤回。这一条直接对应评分细则里的"诱导转账"。

**[严重] §6 §7 — 间接注入的防御只写了"分区"，没有机制。**
- 证据：U18 写了"只作数据"，§6 写了"用户输入、外部描述与工具指令分区"，但规划用的 LLM 仍然会读到商户名和备注原文。分区靠的是 prompt 里的分隔符，模型照样可能听从备注里的指令，提出一笔用户没要求的转账。服务端授权确实能挡住"未确认就执行"，可用户面前已经弹出了一张确认卡，粗心的用户一点就通过了。
- 建议：用 plan-then-execute。工具定义声明 `untrusted_output_fields`，这些字段永远不进入规划器的上下文，只交给不能调用工具的回复生成器。另外，校验器要拒绝"参数来源于不可信字段"的写步骤。

**[严重] §10 §12 — 技术栈太重，和 2 人基准、11-02 截止对不上。**
- 证据：PostgreSQL、SQLAlchemy 加 Alembic、LangGraph、独立 worker（租约加 `SKIP LOCKED`）、独立沙箱容器、PWA、Web IM、飞书、Playwright、Hypothesis，加起来 11 项基础设施。M1 还要求 10-28 当天"同一交易从 App 和 IM 发起都能跑通"，可飞书应用配置、身份绑定、卡片回调本身就要半天以上。
- 建议：
  - IM 挪到 P3；
  - 删掉 LangGraph（理由见下一条）；
  - 存储改用 SQLite，所有写事务用 `BEGIN IMMEDIATE`。SQLite 天然只有一个写者，日累计的并发竞争直接消失；演示数据隔离也简单，一个 demo run 就是一个 db 文件。数据访问层用 SQLAlchemy，保留以后换 Postgres 的可能。

**[中等] §10 — LangGraph 加自定义 DAG 调度器，等于维护两套状态机。**
- 证据：§10 写着"LangGraph 管对话生命周期，业务 DAG 管资金操作"，结果是 LangGraph checkpoint 和 `plan_nodes` 表两套持久化，中断和恢复时必须保持同步，这正是最难测的那类 bug。对话状态本身只有槽位、最近实体和当前计划 ID，一张表就放得下。
- 建议：不用 LangGraph，对话状态和计划状态都由同一个数据库状态机管理。

**[中等] §11 — 每轮评测 420 次 LLM 运行，没法每天迭代。**
- 证据：140 个用例各跑 3 次，按每条 5 到 10 次 LLM 调用、每次 3 到 5 秒算，串行跑一轮要 2 到 5 小时，还要烧额度。
- 建议：分两层。冒烟集大约 60 条，每次合并都跑；全量 310 条只在冻结前跑 2 次。确定性测试（策略、账务、凭证）不经过 LLM，每次提交都跑。

**[中等] §2 §5 — 用 TOTP 当第二因子，评委线上评审时几乎没法完成红色任务。**
- 证据：评委要先装验证器 App、扫码，才能测任何红色操作。如果在 README 里公开 TOTP 秘钥，它就等于密码，不再是独立因子。brief 写的是"人脸识别、短信验证码或 U 盾等"，没有提 TOTP。
- 建议：用"真实校验加模拟投递"的短信 OTP。验证码真随机、一次性、绑定凭证摘要、5 分钟有效、有限流，这些都是真的；只是投递渠道模拟成一个独立的"模拟手机"页面，代表带外设备，和 App 页面分开。再加一个模拟人脸（活体动画加确认），界面上标明"模拟"。TOTP 留作可选的第二种方式。

**[中等] §2 C05 — 挂失只有 R，没有快速止损通道。**
- 证据：用户说"卡丢了"，系统先要 TOTP。用户手忙脚乱的这段时间，卡还能被刷。这一点体验和安全两头都输。
- 建议：先做"临时冻结"，按保护性操作处理，判 Y，一次点击就生效；然后再走 R 级挂失。规则上要不对称：加保护降级，解除保护升级。

**[中等] §2 X01–X04 — 跨场景联动只做了生日一个例子。**
- 证据：brief 原文是"例如：识别生日需求…"，生日只是举例。评委很可能换一个联动需求来测通用性，比如"这个月外卖花超了，帮我管住"，或者"我卡好像被盗刷了"。
- 建议：再加 2 个编排：超支管控（分析、按商户类别设限额、设提醒），以及盗刷处置（发现异常、冻结、挂失、补卡、争议）。这两个能顺带证明 DAG 和授权模型是通用的。

**[中等] §6 — 防幻觉只管结果卡，聊天文字没有检查。**
- 证据：原文是"模型生成的文字若包含无法绑定工具结果的资金数字，不进入交易结果卡"，可回复正文照样可以编数字，比如"你上月外卖花了 1,234 元"。
- 建议：对回复正文做数字溯源检查。抽出金额、日期、笔数、尾号、人名，在本轮工具结果里找不到就重新生成，还不行就改用模板回复。

**[中等] §10 §14 — 只有一个托管模型，没有备用，也没回答数据出境。**
- 证据：§10 写"单一……托管模型"。评审期间，模型服务或中转站一宕机，系统就整体不可用。另外这是银行题，"金融数据是否出境"几乎是必问题。
- 建议：provider 抽象，主模型和一个国产备用模型都跑一遍评测，失败时自动切换。

**[轻微] §9 — Web IM 客户端投入产出比低。**
- 证据：它本质上是第二个聊天界面，作为"IM 渠道"的证据分量不高。不过它确实能让评委亲手测 IM 侧的安全行为（红色跳 App、按钮防重放）。
- 建议：保留，但必须做薄，复用 App 的聊天组件，只换网关和身份；排在飞书之后。

**[轻微] §12 — 2 人方案里，队长一个人同时负责 A（安全内核）和 C（规划），又是集成人。**
- 建议：安全内核和规划器之间只通过契约交互。第二个人在 M2 之后接手红队集，避免"写安全的人自己测安全"。

## 二、它比我好，我采纳

1. 订阅查询判 Y，这是 brief 原文规定的。我判成 G，是误读赛题。
2. 金额一律用整数分（`amount_minor`），我原来用的是 decimal 字符串。
3. 日累计要处理并发：两笔 600 元同时提交，不能都按黄色通过。我原方案没考虑并发。改成用 SQLite 的 `BEGIN IMMEDIATE` 加提交前复核来实现。
4. 超时后状态为 `unknown` 时，只能按原 `operation_id` 去查结果，不能重发；未知状态的金额保留占用。
5. 定时任务用持续授权 mandate，限定对象、上限、次数和时间窗口，可撤销，执行时重新评估。我原来只写了"执行时重新判级"，不够。
6. 当天发生的退款不冲减日累计，防止"转出、退款、再转出"的循环。
7. 银行提交事务里再做一次所有权和授权复核，形成纵深防御，不只依赖上游。
8. 流水要有 12 个月，否则做不出年度报告。我原来写的 6 个月是错的。
9. 理财赎回和实体卡申请判 R。brief 没有明说，但更严的判法不会丢分，体验上的代价也很小。
10. 演示时钟不影响 OTP 和凭证的有效期；每次演示用独立的 `demo_run_id`。
11. 群聊里不回传私密内容（U10）。
12. 指标里写明"这些是目标，不是结果"，并报告误拒率。
13. 生日订单按鲜花、蛋糕拆成两笔，部分成功时走 Saga。
14. 沙箱：我原来主张"只用 DSL、不生成代码"，评委可能会认为这是在回避"生成的代码要在沙箱里运行"这一要求。改成双路径：常规分析走 DSL；"自定义分析"让模型生成代码，在 `network_mode: none` 的容器里运行，加 AST 白名单和资源限制。这样两条路径都能演示。

## 三、我比它好，它应当采纳

1. 反诈信号加延时到账（见第一部分第 1 条）。
2. 用 plan-then-execute 隔离不可信字段（见第一部分第 2 条）。
3. 保护性操作快速通道，规则不对称（见第一部分第 7 条）。
4. 回复正文的数字溯源检查（见第一部分第 9 条）。
5. 多加 2 个跨场景编排，证明通用性（见第一部分第 8 条）。
6. 备用模型加数据出境的回答（见第一部分第 10 条）。
7. 一个计划只出一张确认卡。我的方案写明了；它的方案虽然有"整批预览"，但没规定确认的粒度。
8. 中文金额和相对时间用确定性解析器处理，不交给 LLM 猜。它的 IntentFrame 里 `amount_minor` 是模型直接填的。
