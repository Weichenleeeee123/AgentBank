## 必须修复的发现

### F1 / P1：同一对话重复查询会返回旧余额

- 位置：`backend/agentbank/agent/orchestrator.py:173`，以及 `bank/capabilities_full.py:59–65`。
- 复现：同一对话“查余额”→“给房东转20元”→确认成功→再次“查余额”。
- 实测：第一次为 500000 分；转账状态 succeeded；第二次仍返回 500000 分且复用了第一次的 record。独立余额 API 已为 498000 分。浏览器重复点击“查余额”同样复现，as_of 也仍是旧时间。
- 原因：幂等键只由 conversation_id 和文本生成；查询也命中永久业务结果缓存。相同文本的新用户消息与网络重试被混为一谈。
- 修复验收：按消息/请求 ID 区分新操作和重试；查询应读取当前事实；同一会话转账前后相同查询反映余额变化，同时重复提交同一写请求仍不得重复记账。

### F2 / P1：PIN 安全表单提交后无法继续授权

- 位置：`frontend/app.js:388–409`，特别是 406 行。
- 复现：主页“修改 PIN”→两次输入相同有效四位 PIN→“提交安全请求”。
- 实测：API 返回 `awaiting_confirmation`、`assurance=mfa`；前端只识别 `awaiting_mfa`，把其他状态渲染为 result，因此没有“确认执行”或“输入验证码”按钮。操作停留在 prepared 状态。
- 修复验收：正确呈现确认→MFA→终态全链路，并用浏览器覆盖；不能把“请求已提交”当成功。还应取消硬编码 `card_001`，选择当前用户自己的卡。

### F3 / P1：金额与状态事实片段渲染错误

- 位置：`frontend/app.js:19–31`。
- 复现：点击“查余额”，再完成一笔黄色转账。
- 实测：同一余额卡同时显示 `可用余额 500000` 和 `可用余额 ¥5000.00`；成功转账卡显示 `操作状态 0`，真实 succeeded 藏在原始 JSON 中。
- 原因：金额单位根据中文 label 是否以 `_minor` 结尾推断，而非片段的 `value_minor` 字段；`value_minor ?? status` 又让占位数值 0 遮盖状态。
- 修复验收：按事实片段类型/字段转换分为元，状态使用固定文案，去重；金额、币种、处理中/成功/未知都必须与后端事实一致。

### F4 / P1：IM 每条消息新建会话，无法多轮补槽

- 位置：`backend/agentbank/api/app.py:738`；飞书模拟适配器也有同样模式（`channels/feishu.py:41`）。
- 复现：同一用户连续签名发送两个不同 event_id 的 Web IM 消息：“给房东转账”→“20元”，即使 payload 带同一个 conversation_id。
- 实测：第一条追问金额，第二条变成无法识别业务；App 在同一个 conversation_id 下则正确返回 clarification→confirmation。
- 原因：event_id 被用作 conversation_id 的组成部分，消息去重键与会话身份混用。
- 修复验收：以用户/渠道/聊天身份隔离并持续上下文；event_id 只用于去重。覆盖补槽、指代、改金额、取消及重启后的会话恢复。
